# Рекомендаційний модуль — прототип до магістерської роботи

Прототип серверної частини рекомендаційної підсистеми вебзастосунку
**«Інформаційна система багатокритеріального аналізу та підбору страхових програм»** (магістерська робота,
Данильченко Володимир Григорович, група МІПм12514д, Київський університет
імені Бориса Грінченка).

Прототип демонструє й дозволяє відтворити роботу описаного в
пояснювальній записці контентно-орієнтованого алгоритму ранжування
програм добровільного медичного страхування (ДМС) з жорсткими
обмеженнями та їх послабленням (hard-constraint content-based ranking
with relaxation) — див. `src/lib/recommendation.ts`.

## Про розробку

Код написаний автором роботи з активним використанням інструментів
на основі штучного інтелекту (AI-асистована розробка: генерація
шаблонного коду, рефакторинг, юніт-тести та бенчмарки) — це вказано
тут з міркувань академічної доброчесності. Алгоритмічні рішення,
формальний опис моделі, вибір критеріїв та ваг ранжування (розділ
1 пояснювальної записки) належать автору.

## Технологічний стек

- **Bun** — середовище виконання JavaScript/TypeScript
- **Hono** — легкий HTTP-фреймворк
- **oRPC** — типобезпечний RPC-шар API (процедури на `/api/rpc/*`)
- **Drizzle ORM** + **SQLite** (локальний файл) — рівень даних
- **Zod** — валідація вхідних даних
- **bun:test** — юніт-тестування

## Структура проєкту

```
insurance-recommender/
├── src/
│   ├── db/
│   │   ├── schema.ts     — схема БД (insuranceProducts, coverageComponents, recommendationRequests)
│   │   ├── client.ts     — підключення до локальної SQLite-бази
│   │   ├── catalog.ts    — синтетичні дані без операцій БД
│   │   └── seed.ts       — наповнення демонстраційної БД
│   ├── lib/
│   │   ├── profile.ts        — спільна валідація профілю й ваг
│   │   └── recommendation.ts — рекомендаційний алгоритм (ядро прототипу)
│   ├── routes/
│   │   └── recommend.ts  — oRPC-процедури: getRecommendations, listCatalog, getProduct
│   ├── app.ts             — складання HTTP-застосунку (Hono + oRPC, CORS, /api/health)
│   ├── router.ts          — композиція маршрутизатора
│   └── server.ts          — точка входу сервера
└── tests/
    ├── recommendation.test.ts — юніт-тести алгоритму (жорсткі обмеження, послаблення, ранжування)
    ├── regression.test.ts     — регресійні тести дефектів
    ├── api.test.ts            — інтеграція Hono/oRPC/SQLite в ізольованій БД
    ├── evaluate.ts            — 10 сценаріїв, 5000 профілів, аналіз чутливості
    └── benchmark.ts           — function-only бенчмарк без БД/мережі
```

## Встановлення та запуск

```bash
bun install
cp .env.example .env

# створити таблиці в локальній SQLite-базі
bun run db:push

# наповнити каталог ілюстративними даними
bun run seed

# запустити сервер (http://localhost:3000)
bun run start
```

## API (oRPC, `/api/rpc/*`)

| Процедура | Призначення |
|---|---|
| `recommend.getRecommendations` | Ранжований список рекомендованих програм ДМС для профілю користувача |
| `recommend.listCatalog` | Повний каталог продуктів |
| `recommend.getProduct` | Одна програма з деталізованими компонентами покриття |

`getRequestLog` вилучено з публічного API до реалізації автентифікації.
Журнал продовжує записуватися локально; конфіденційність файла та строки
зберігання мають забезпечуватися окремо. Це не готовий промисловий сервіс.

Перевірка стану сервера: `GET /api/health`.

## Тести та бенчмарк

```bash
bun test --coverage   # 45 тестів: 15 базових, 20 регресійних, 10 API
bunx tsc --noEmit      # статична перевірка
bun tests/evaluate.ts  # детермінована сценарна перевірка й аналіз чутливості
bun run benchmark     # час recommend, включно з валідацією, без IO/мережі
```

Повні результати зберігаються в `artifacts/evaluation.json` і
`artifacts/benchmark.json`. Seed генератора профілів: `20261005`;
профілі й склад каталогу відтворювані, час виконання залежить від середовища.

## Виправлення за рецензією (18.10.2026)

- Регіон C2 не послаблюється; R3 вилучено, оскільки `nationwide` вже дозволено C2.
- C8 вимагає позитивний скінченний ліміт кожного обов’язкового типу покриття.
  `complex` не означає всі послуги: комплексний запит вимагає ambulatory і stationary;
  maternity/dental/chronic та інші потреби перевіряються окремо.
- Типи компонентів зберігаються в `coverage_components.coverage_type`.
  Для старої БД після резервної копії див. `migrations/20261018_coverage_type.sql`;
  legacy `unknown` не підтверджує покриття. Жодної автоматичної зміни реальної БД.
- Ваги в API та алгоритмі: скінченні, невід’ємні, ефективна сума скінченна й >0.
  Відсутні поля використовують евристичні defaults, явні нулі зберігаються.
- Сталий критерій нейтральний (0.5) і для вигоди, і для витрат.
  Пояснення відокремлює відносні внески від франшизи, очікування та послаблень.
- Невідомі спеціальні потреби відхиляються. Семантичного NLP-розпізнавання немає.

Результат перевірки: 45/45 тестів, 10/10 сценаріїв; 3128/5000 порожніх
відповідей (62.56%), 3571 із послабленнями (71.42%). Збільшення порожніх
відповідей не означає погіршення правильності: раніше відсутнє покриття
та чужий регіон могли допускатися помилково. Аналіз min-max виявив
13 змін взаємного порядку у 1325 порівняннях пар; це не незалежні
ринкові спостереження. Оцінки відносні, не ймовірності придатності.

Приклад запиту: `{ "age": 30, "region": "Львів", "requiredProgramType":
"maternity", "maxBudget": 30000, "minCoverageLimit": 150000,
"specialNeeds": ["материнство"] }` повертає лише синтетичну програму ID6.
Перевірка наявності компонента не є експертною валідацією договору.

## Застереження щодо даних

Дані каталогу продуктів у `src/db/seed.ts` є **ілюстративними** —
створені для демонстрації роботи алгоритму, а не є витягом із реальних
чинних тарифів страхових компаній. Назви компаній використані лише як
приклад ринкових гравців.
